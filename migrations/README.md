# Миграции

У каждой задачи своя схема PostgreSQL, и схемы разошлись: `pprof_2` пишет коммерческие
страницы услуг, и набор колонок у него другой. Поэтому раскладка такая:

| Каталог | Чья схема | Чем применяется |
|---|---|---|
| `migrations/task_1/` | `public` | docker-entrypoint при первой инициализации volume; руками для уже существующей базы |
| `migrations/pprof_1/` | `pprof_1` | только руками, только к своей схеме |
| `migrations/pprof_2/` | `pprof_2` | только руками, только к своей схеме |
| `migrations/obuch_1/` | `obuch_1` | только руками, только к своей схеме |
| `migrations/obuch_2/` | `obuch_2` | только руками, только к своей схеме |
| `migrations/pprof_fix_1/` | `pprof_fix_1` | только руками, только к своей схеме |
| `migrations/pprof_fix_2/` | `pprof_fix_2` | только руками, только к своей схеме |
| `migrations/pprof_fix_3/` | `pprof_fix_3` | только руками, только к своей схеме |
| `migrations/pprof_fix_4/` | `pprof_fix_4` | только руками, только к своей схеме |
| `migrations/pprof_fix_5/` | `pprof_fix_5` | только руками, только к своей схеме |
| `migrations/pprof_audit_1/` | `pprof_audit_1` | только руками, только к своей схеме |
| `migrations/pprof_audit_2/` | `pprof_audit_2` | только руками, только к своей схеме |
| `migrations/site/` | `site` | только руками; каталог dpoprof.ru, не принадлежит задаче |
| `migrations/site_obuchim/` | `site_obuchim` | только руками; каталог obuchim-specialista.ru |

**Схемы каталогов — исключение, и их две.** Это каталоги услуг площадок: программы, их
рубрики и наши профессии. Каталог принадлежит сайту, а не задаче: две задачи одной площадки
видят один каталог, задачи разных — разные. `repository.ValidateSchema` их не проверяет — в
схемах задач этих таблиц нет вовсе. Собираются они не миграцией, а командой
`make <задача> catalog-sync`; миграция заводит только пустые таблицы:

```bash
docker exec -i seo-postgres psql -U seo -d seo -v ON_ERROR_STOP=1 \
  -f - < migrations/site/000001_schema.up.sql
docker exec -i seo-postgres psql -U seo -d seo -v ON_ERROR_STOP=1 \
  -f - < migrations/site_obuchim/000001_schema.up.sql
```

Схема на площадку, а не колонка площадки в общей таблице, — решение осознанное: сбор
начинается с `DELETE FROM <схема>.programs`, и один забытый `WHERE site = ...` стёр бы
каталог соседа молча. Какую схему взять, решает не задача, а таблица `catalogSites` в
composition root: профиль называет только площадку (`Profile.CatalogSite`), и пара «сайт
одной площадки — схема другой» невыразима. Таблицы у обеих схем одинаковые, и расходиться им
нельзя: подбор услуг читает их одним и тем же кодом.

**Общего каталога больше нет.** У каждой задачи свой, и открывает его baseline — один файл,
описывающий всю её схему целиком. Дальше идут обычные пронумерованные миграции: у `pprof_1`
это `000002_seo_title.up.sql`, добавляющая колонку короткого заголовка выдачи, у `obuch_1` —
`000002_course_url.up.sql`, адрес курса для кнопки призыва. Правило
«применённый baseline не правят» остаётся в силе для `task_1` и `pprof_1`: у них живые
статьи, и новая колонка приезжает отдельным файлом, а не правкой `000001`. У `obuch_1`
причина та же: статья 1 уже опубликована, и её входные данные пересобирать нечем.

Смешивать каталоги нельзя: `migrations/task_1/` заведёт в схеме `pprof_2` колонки,
которых у неё быть не должно, и `repository.ValidateSchema` остановит первую же её команду на
«unexpected column». Наоборот — то же самое.

Проверка схемы строгая в обе стороны: колонка, объявленная профилем задачи
(`Profile.ExtraInputColumns`), обязана быть в схеме, а не объявленная — обязана отсутствовать.
Расхождение видно на старте, а не пустым полем в `result.md` через два часа генерации.

## Новая схема с нуля

```bash
docker exec -i seo-postgres psql -U seo -d seo -c 'CREATE SCHEMA IF NOT EXISTS pprof_2'
docker exec -i seo-postgres psql -U seo -d seo -v ON_ERROR_STOP=1 \
  -c 'SET search_path TO pprof_2' -f - < migrations/pprof_2/000001_schema.up.sql
```

Для `pprof_1` — то же самое со своим именем схемы и своим файлом. Схема `task_1` — это
`public`, и `search_path` ей не нужен.

## Правки

Применённый файл не правят: он уже накатан на живые базы, и правка разошлась бы с тем, что
в схеме на самом деле. Новое изменение — новый файл `NNNNNN_имя.up.sql` рядом со своим
`.down.sql` в каталоге той схемы, которой оно касается.

Исключение — задача, схему которой можно пересобрать с нуля: у `pprof_2` входные данные
восстанавливает повторный `import` из книги, а остальное — прогон, поэтому её baseline
переписывается целиком, а схема сносится и создаётся заново. У `pprof_1` и `task_1` в
таблицах живые статьи, и так делать нельзя — их baseline описывает то состояние, к которому
схему уже привели прежние миграции, и потому идемпотентен.

Разрешением этим пользуются по надобности, а не по привычке: числа программы у `pprof_2`
(`000002_program_facts`) пришли отдельным файлом, хотя baseline переписать было можно. Причина
в том, что сносить схему — значит стереть `articles` вместе с отметками `wordpress_status`, а
они защищают живой блог от второй записи той же страницы. Пересборка остаётся для случая,
когда схему меняют до первой публикации.

## Тесты

Тесты репозитория собирают схему по `migrations/task_1/*.up.sql` — то есть схему задачи,
пишущей статьи блога. Тестам задачи с другим набором колонок передаётся её каталог:
`migrations/pprof_2/` вместо `task_1`, а не вместе с ним.
