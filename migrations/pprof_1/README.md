# Миграции схемы `pprof_1`

Применяются только к схеме `pprof_1` и только руками:

```bash
docker exec -i seo-postgres psql -U seo -d seo -v ON_ERROR_STOP=1 \
  -c 'SET search_path TO pprof_1' -f - < migrations/pprof_1/000001_schema.up.sql
```

`000001_schema.up.sql` описывает схему целиком и заменяет собой общий каталог `migrations/`.
Он идемпотентен (`IF NOT EXISTS` у всего), поэтому применение к живой схеме ничего не меняет:
она уже приведена к этому состоянию общими миграциями `000001`–`000004`.

**Живые данные.** В таблицах `pprof_1` лежат настоящие статьи. `000001_schema.down.sql`
сносит их вместе со схемой — запускать его на рабочей базе нельзя.

Необязательные колонки, которые задача объявляет в `Profile.ExtraInputColumns`: `author`,
`links`, `professions`, `tags`. Те же самые есть у `task_1` — это набор задачи, которая пишет
статьи блога. Плюс `article_metadata.tldr`: его пишет стадия `info`.

Колонок `pprof_2` (`seo_title`, `section`, `profession`, `teachers`, `service_name`) здесь нет
и быть не должно: проверка схемы строгая в обе стороны, и чужая колонка — такая же ошибка,
как отсутствующая.

Появится своё поле — новый файл в этом каталоге плюс строка в `Profile.ExtraInputColumns`.
Применённый `000001_schema.up.sql` при этом не правят: он уже накатан на живую базу.
