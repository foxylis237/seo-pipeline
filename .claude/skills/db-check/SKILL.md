# Проверка схемы

Три источника правды о схеме расходятся молча:

1. **`migrations/*.up.sql`** — что должно быть создано;
2. **`expectedSchema`** в `internal/tasks/task1/repository/schema.go` — что требует код
   ([ADR-0003](../../../docs/adr/0003-validate-schema.md));
3. **фактическая БД** — что реально есть в volume.

Расхождение 1↔2 останавливает приложение целиком при следующем запуске. Расхождение 2↔3
не замечается вовсе, пока volume не пересоздадут. Проверка дешёвая, стоимость пропуска высокая.

## Почему расходятся

Миграции применяются docker-entrypoint'ом PostgreSQL **только при первой инициализации
volume**. Отдельного runner'а нет. Разработчик добавил миграцию — у него локально она
не применилась, потому что volume уже существует.

## Шаг 1. Миграции ↔ `expectedSchema`

Собрать колонки из миграций и сверить со списком в `schema.go`. Учитывать `ALTER TABLE ...
ADD COLUMN` в поздних миграциях, а не только `CREATE TABLE` в первой.

**Расхождение «в миграции есть, в `expectedSchema` нет»** — не всегда дефект: `ValidateSchema`
проверяет наличие ожидаемых колонок, лишние в БД её не смущают. Но это значит, что колонка
не используется кодом — проверить, не повтор ли это M4.

**Расхождение «в `expectedSchema` есть, в миграциях нет»** — всегда дефект: приложение
не стартует на чистом volume.

## Шаг 2. `expectedSchema` ↔ фактическая БД

```
docker compose up -d --wait postgres-dry-run
docker compose exec -T postgres-dry-run psql -U seo -d seo_dry_run -c '\d+ articles'
```

Сверять то же, что сверяет `ValidateSchema`: имя колонки, тип, nullable, каскадные FK.

Быстрее и надёжнее — прогнать саму проверку через тесты репозитория:

```
TEST_DATABASE_URL='postgres://seo:seo@localhost:5433/seo_dry_run?sslmode=disable' \
  go test -count=1 ./internal/tasks/task1/repository/...
```

## Шаг 3. `CHECK`-констрейнты

Отдельная категория, которую легко пропустить: `articles.status` и `articles.current_step`
ограничены списками значений.

```sql
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
WHERE conrelid = 'articles'::regclass AND contype = 'c';
```

Сверить со значениями, которые код реально записывает (`SET current_step = '...'` в
`article_repository.go`) и со списком в [docs/CONTEXT.md](../../../docs/CONTEXT.md).

Значение, которое код пишет, а констрейнт не допускает, даёт ошибку только на конкретной
статье в конкретный момент — то есть посреди оплаченного прогона.

Добавление значения делается дропом и пересозданием констрейнта целиком; образец —
`migrations/000005_add_article_review_stage.up.sql`.

## Шаг 4. Семантика колонок путей

Проверено 2026-08-05: имена колонок в `article_outputs` **не соответствуют содержимому**.

| Колонка | Что лежит |
|---|---|
| `metadata_path` | `review.txt` |
| `final_path` | `fixed_article.txt` |
| `word_count` | ничего, только обнуляется |

Плюс NULL-ность этих колонок работает как маркер прогресса в `GetPendingForOperation` —
то есть колонка входит в машину состояний, а не просто хранит путь.

При любой правке этих колонок проверять оба смысла: и что пишется, и какой предикат
выборки от этого зависит.

## Шаг 5. Парность миграций

У каждой `NNNNNN_name.up.sql` обязана быть `.down.sql`. Проверить, что `down` действительно
откатывает `up`, а не пустой.

```
ls migrations/ | sed 's/\.\(up\|down\)\.sql//' | sort | uniq -c | grep -v '^ *2 '
```

**Пройден:** вывод пуст.

## Отчёт

По каждому из пяти шагов — сошлось или нет, с конкретным именем таблицы и колонки.
Найденный дрейф — с указанием, какой из трёх источников считать правильным и почему.

Ничего не править молча: правка `expectedSchema` без миграции и наоборот — это и есть
способ, которым дрейф появляется.
