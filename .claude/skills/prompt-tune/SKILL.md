# Правка промпта

Шесть промптов в `tasks/task_1/prompts/`, 453 строки суммарно:

| Файл | Строк | Стадия |
|---|---|---|
| `structure.txt` | 20 | `structure` |
| `article.txt` | 193 | `article` |
| `article_info.txt` | 46 | `info` |
| `review.txt` | 86 | `review` |
| `fix_article.txt` | 37 | `fix` |
| `html.txt` | 71 | `html` |

Промпт — это `text/template`, отрендеренный `Router` перед отправкой. Ошибка в плейсхолдере
проявляется в рантайме, а не при сборке.

## Шаг 1. Понять, что стадия получает на вход

Существующие плейсхолдеры во всех шести промптах:

```
{{.Title}}  {{.Article}}  {{.Structure}}  {{.GeneratedStructure}}
{{.Keywords}}  {{.LSIWords}}  {{.Links}}  {{.Professions}}  {{.Review}}
```

**Новый плейсхолдер требует правки кода**, а не только текста: поле должно быть в структуре
`Data`, которую стадия передаёт в `Call`. Промпт с неизвестным полем упадёт при рендере.

Проверить, откуда поле берётся, до правки — через `go_search` по имени поля.

Отдельно помнить: `run <external_id>` вызывает стадию `article` с **пустыми**
`{{.GeneratedStructure}}`, `{{.Keywords}}`, `{{.LSIWords}}` (L8). Промпт должен вести себя
осмысленно при пустых значениях, а не выдавать заглушку в текст статьи.

## Шаг 2. Учесть, что стадия не последняя

Выход стадии — вход следующей. Цепочка:

```
structure → article + info → review → fix → html → result
```

Правка формата вывода ломает разбор ниже по цепочке:

- **`info`** — единственная стадия, чей ответ **парсится**, а не передаётся как текст:
  `article.ParseArticleInfo` вытаскивает теги, TL;DR, FAQ. Изменение формата ответа обязано
  сопровождаться правкой парсера и его тестов (`article_info_test.go`, покрытие 98.6%).
- **`html`** — ответ проходит `normalizeAndValidateHTML`. Требования к разметке живут
  в валидаторе, а не только в промпте.
- **`review`** — результат попадает в `{{.Review}}` промпта `fix`. Смена структуры замечаний
  требует согласованной правки `fix_article.txt`.
- **`structure`** — результат попадает в `{{.GeneratedStructure}}` промпта `article`.

## Шаг 3. Проверить настройки стадии

`config/config.yaml` → `llm.stages.<stage>`. Промпт вырос вдвое — проверить `max_tokens`
и `timeout`. У `fix` уже `timeout: 300s`, и таймауты умножаются на число targets (H6):
двойной запас здесь стоит десять минут на статью.

`temperature` менять осознанно: для `structure` и `html` низкая температура уместнее,
для `article` — выше.

## Шаг 4. Проверить правку

**Не запускать `make task-1 generate` ради проверки промпта** — это деньги на LLM и
трафик к внешним сервисам, а обратная связь придёт через минуты.

Быстрая проверка рендера без вызова LLM:

```
go test ./internal/llm/... ./internal/tasks/task1/generation/...
```

Если рендер промпта не покрыт тестом — это и есть первый шаг: тест, который рендерит шаблон
с типовыми данными и проверяет, что все плейсхолдеры подставились и пустые значения
не дают мусора.

Сквозная проверка — `make task-1 dry-run`, но он **сейчас сломан** (C1/C2). Падение
на подмене модели — известная проблема, не регрессия промпта.

Реальный прогон на одной статье — `make task-1 <stage> <id>` — только по явной просьбе.

## Шаг 5. Зафиксировать намерение

Промпт — это спецификация поведения, а не текст. Существенная правка (сменился формат
вывода, добавилось требование к структуре) заслуживает строки в сообщении коммита,
объясняющей **зачем**, а не только **что**.

Изменение, меняющее контракт между стадиями, — повод для ADR.

## Отчёт

Что изменено, какие плейсхолдеры затронуты, какие стадии ниже по цепочке зависят от формата
вывода и проверены ли они, и чем именно проверена правка. Если проверка ограничилась
рендером без вызова LLM — сказать это прямо.
