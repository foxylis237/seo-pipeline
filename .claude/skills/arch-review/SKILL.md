# Architecture Review

Разобрать `$ARGUMENTS` (по умолчанию — проект целиком) на предмет архитектурных границ.
Не стилистика, не баги — граница и связанность.

Работает в изолированном контексте, поэтому основная сессия не засоряется чтением файлов.
Возвращается только разбор.

## Критерии

Установка проекта — [ADR-0006](../../../docs/adr/0006-architecture-principles.md) и
[.claude/rules/architecture.md](../../rules/architecture.md). Коротко: Clean Architecture
как границы без новых слоёв, DDD тактически, **OCP — главный критерий**.

Проверять по четырём осям:

**1. Направление зависимостей.** Бизнес-сценарий не знает про CLI, PostgreSQL, Playwright
и конкретных LLM-провайдеров. Известные нарушения: `internal/llm` импортирует
`internal/config` (M9), `generation.Pipeline` зависит от конкретного `*llm.Router` (M8).
Найти новые — и проверить, не появилось ли цикла (`go list -deps`).

**2. OCP.** Задать вопрос: «что придётся изменить, чтобы добавить седьмой этап пайплайна,
третью SEO-интеграцию, четвёртого LLM-провайдера, вторую точку входа?»

Ответ «ничего, кроме регистрации» — граница верная. Ответ «switch в `main.go`, ещё один
метод интерфейса на 13 методов, ещё один `Stage*` во writer, ветка в `GetPendingForOperation`» —
граница проведена не там. Сегодня ответ второй.

**3. Место объявления интерфейса.** Интерфейс объявляется у потребителя и держится узким.
`PipelineRepository` на 13 методов (M7) — образец того, как не надо: любой тест обязан
реализовать всё целиком.

**4. Путь к EDA/VSA не закрыт.** Этапы остаются независимыми и адресуемыми по имени,
состояние перехода живёт в БД, а не в структуре вызовов. Замена прямого вызова на публикацию
события должна оставаться локальным изменением.

## Порядок

1. Прочитать [docs/CONTEXT.md](../../../docs/CONTEXT.md) — разбор ведётся в терминах проекта.
2. Свериться с [бэклогом аудита](../../../docs/AUDIT-2026-08.md): часть находок уже описана.
   Повторять их незачем — ссылаться по номеру и отмечать, изменилось ли положение.
3. Построить фактическую картину зависимостей области: `go_package_api`, `go_file_context`,
   `go_symbol_references`. Не по именам файлов и не по предположениям — по компилятору.
4. Проверить четыре оси выше.
5. Для каждой найденной проблемы: **где граница проходит сейчас**, **где должна**,
   **что сломается при переносе**, **какой минимальный шаг двигает в нужную сторону**.

## Чего не делать

- Не предлагать слои и папки (`domain/`, `usecase/`, `infrastructure/`) — прямо отклонено
  в ADR-0006.
- Не предлагать агрегаты, bounded contexts, domain events, EDA и Vertical Slice —
  отложены сознательно.
- Не предлагать рефакторинг «чтобы соответствовало шаблону». Причина изменения — снижение
  связанности, повышение понятности или упрощение расширения. Нет такой причины — нет находки.
- Не редактировать файлы. Это разбор.

## Результат

Список находок, отсортированный по тому, сколько будущей работы каждая экономит.
Для каждой — минимальный первый шаг, который можно сделать отдельным коммитом,
не ломая работающее.

Новые находки, которых нет в бэклоге аудита, назвать явно — их нужно будет туда добавить.
