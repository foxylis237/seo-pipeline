# ADR-0007. Слои конфигурации Claude Code: проектный рабочий, универсальный отложенный

**Статус:** принято 2026-08-05
**Затрагивает:** `.claude/`, `~/.claude/shared/go-rules/`, `~/.claude/skills/`

## Контекст

Конфигурация Claude Code для проекта выросла до пяти правил, девяти скиллов и четырёх хуков.
Часть содержимого универсальна для любого Go-проекта (обёртка ошибок, `defer` для
завершителей, узкие интерфейсы, цикл gopls), часть привязана к этому репозиторию (имена
интеграций, baseline линтера, `TEST_DATABASE_URL`, двенадцать точек добавления стадии).

Возникло желание вынести универсальную часть в пользовательский уровень, чтобы переиспользовать
её в других проектах. Документация Claude Code описывает `~/.claude/rules/` как механизм
«личных правил, применяющихся ко всем проектам».

## Проверка

Перед переносом поведение измерено хуком `InstructionsLoaded`, который логирует, какие файлы
инструкций загружаются, когда и почему. Прогон 2026-08-05, шесть триггерных файлов.

**Результат 1: правила из `~/.claude/rules/` не загружаются.** За всю сессию ни одной записи
с `memory_type: "User"` — ни при старте, ни по совпадению путей. Проектные правила в той же
сессии грузились штатно с `memory_type: "Project"` и `load_reason: "path_glob_match"`.
Правила существовали на диске до старта сессии, так что это не эффект отложенного подхвата.

**Результат 2: паттерны `paths:` с многосегментным префиксом не срабатывают.**

| Паттерн | Результат |
|---|---|
| `**/*.go` | срабатывает |
| `migrations/**` | срабатывает |
| `internal/llm/**` | не срабатывает |
| `internal/integrations/**` | не срабатывает |
| `internal/llm/deepseekweb/**` | не срабатывает |
| `tasks/task_1/prompts/**` | не срабатывает |

Практическое следствие для проекта: `playwright.md` и `llm-stages.md` не подключались никогда,
`repository-sql.md` работал только половиной своих паттернов. Около 125 строк правил лежали
мёртвым грузом.

## Решение

**Рабочий слой — только проектный `.claude/`.** Правила, скиллы и хуки, от которых зависит
работа, живут в репозитории и версионируются вместе с кодом.

**`~/.claude/rules/` не используется.** Каталог намеренно не создаётся: его наличие создавало бы
впечатление работающего механизма.

**Универсальный слой хранится, но не подключён автоматически:**

- `~/.claude/shared/go-rules/` — четыре правила уровня языка, библиотека шаблонов.
  Подключение в новый проект — явное, симлинком: `ln -s ~/.claude/shared/go-rules
  <project>/.claude/rules/shared`. Тогда правила грузятся как проектные, и `paths:` работает.
- `~/.claude/skills/` — шесть скиллов, работающих во всех проектах. Пользовательские скиллы
  загружаются штатно (в отличие от правил), поэтому здесь ничего делать не нужно.

**Имена универсальных скиллов разведены с проектными** (`go-ship` против `ship`,
`grilling-core` против `grilling`). Причина: при совпадении имён **пользовательский уровень
перекрывает проектный** — обратно тому, как устроены правила и настройки. Одноимённый `ship`
в `~/.claude/skills/` молча заменил бы проектный гейт обобщённым.

**Дублирование между слоями принято сознательно.** Проектные правила остаются самодостаточными
и содержат как принцип, так и его здешнее воплощение. Дедупликация создала бы зависимость
работающего репозитория от машинно-локального каталога ради экономии ~130 строк контекста.

## Последствия

- Проект работает без внешних зависимостей: свежий клон получает полную конфигурацию из git.
- Перенос в новый Go-проект — одна команда `ln -s` плюс уже доступные скиллы.
- Универсальный слой не проверяется автоматически при изменениях: он не подключён здесь,
  поэтому регрессия в нём обнаружится только в проекте, куда его подключат.
- Если Claude Code починит поведение `~/.claude/rules/`, переход к нему — перемещение
  четырёх файлов без изменения их содержимого.

## Незакрытый вопрос

Правки `paths:` в `playwright.md`, `llm-stages.md` и `repository-sql.md` (добавлены формы
с ведущим `**/` при сохранении исходных паттернов) **не проверены**: изменённые правила
не перечитываются до перезапуска сессии, а исследование было остановлено сознательно.

Признак, что правка не сработала: при работе с файлами в `internal/integrations/` или
`tasks/task_1/prompts/` соответствующее правило не появляется в контексте. Запасной вариант —
слить содержимое этих правил в правило с `**/*.go`, пожертвовав экономией контекста ради того,
чтобы оно применялось вообще.

## Альтернативы

- **Плагин** (`.claude-plugin/plugin.json`) для универсального слоя — подключение одной строкой
  и без симлинков в домашний каталог. Правильное направление, когда универсальных материалов
  станет больше одного проекта; сейчас преждевременно.
- **Симлинк универсальных правил в этот проект** — дал бы дублирование в контексте, потому что
  проектные правила уже содержат универсальную часть.
- **Вычистить универсальное из проектных правил** — сделало бы репозиторий зависимым
  от машинно-локального каталога.
