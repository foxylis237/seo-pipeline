# ADR-0003. Сверка схемы БД перед каждой командой

**Статус:** принято · задокументировано постфактум 2026-08-05
**Затрагивает:** `repository.ValidateSchema`, `internal/tasks/task1/repository/schema.go`

## Контекст

Миграции применяются docker-entrypoint'ом PostgreSQL **только при первой инициализации
volume**. Отдельного migration runner'а в проекте нет. Отсюда штатная ситуация: разработчик
добавил миграцию, но его локальный volume уже инициализирован — новая колонка не появилась.

Расхождение кода и схемы проявляется поздно и дорого: не при старте, а посреди batch-прогона,
после нескольких оплаченных вызовов LLM, ошибкой уровня `column "..." does not exist`.

## Решение

Перед выполнением любой команды `ValidateSchema` сверяет фактическую схему с ожидаемой,
описанной в `expectedSchema` (`schema.go`): наличие таблиц и колонок, типы, nullable,
наличие каскадных внешних ключей.

Несовпадение — отказ на старте с конкретным описанием расхождения.

## Последствия

- Класс ошибок «код новее схемы» полностью выявляется до первого запроса и до первой траты.
- **Новая миграция обязана сопровождаться правкой `expectedSchema`.** Иначе приложение
  перестаёт запускаться целиком — включая команды, не связанные с новой колонкой.
- Обратная сторона: `expectedSchema` требует колонки, которые код не читает и не пишет
  (`article_metadata.reading_time_minutes`, `article_outputs.word_count`, четыре поля
  `article_inputs`). Удалить их нельзя, не тронув оба места. См. M4 в
  [бэклоге аудита](../AUDIT-2026-08.md).
- Небольшой оверхед на старте — несколько запросов к `information_schema`.

## Альтернативы

- **Полноценный migration runner** (`golang-migrate`, `goose`) с таблицей версий — решает
  первопричину и делает `ValidateSchema` избыточным. Правильное направление, но это
  отдельная работа, а проверка нужна была сразу.
- **Полагаться на ошибки запросов** — то, от чего решение и защищает.
- **Проверять только при старте long-running процесса** — здесь CLI, каждый запуск и есть старт.
