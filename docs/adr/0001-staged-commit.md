# ADR-0001. Двухфазная публикация артефактов с откатом

**Статус:** принято · задокументировано постфактум 2026-08-05
**Затрагивает:** `internal/tasks/task1/output/writer.go`

## Контекст

Стадия пайплайна производит два результата одновременно: файл на диске (`article.txt`,
`result.md`) и запись в БД (путь к файлу + новый `current_step`). Это два разных хранилища
без общей транзакции.

Наивный порядок «записать файл, затем обновить БД» даёт при сбое между операциями файл,
на который никто не ссылается, и статью, застрявшую на предыдущем этапе. Обратный порядок
даёт запись в БД, указывающую на несуществующий файл. Оба состояния требуют ручного разбора,
а стоят они дорого: за каждым артефактом — оплаченный вызов LLM.

## Решение

Артефакт публикуется в две фазы через `articleoutput.Commit(persist, pending...)`:

1. **Stage.** Содержимое пишется во временный файл рядом с целевым, затем `Sync()` —
   данные гарантированно на диске.
2. **Commit.** Для каждого существующего целевого файла создаётся hard-link-бэкап
   (`os.Link` в `.backup-*`), затем `rename` временного файла на место целевого — атомарная
   операция POSIX. После публикации **всех** файлов вызывается `persist` — колбэк,
   сохраняющий состояние в БД.
3. **Откат.** Если `persist` вернул ошибку, каждый опубликованный файл восстанавливается
   из бэкапа обратным `rename`. Ошибки отката собираются через `errors.Join` и не теряются.

`persist` передаётся **внутрь** `Commit`, а не вызывается после него. Это и есть суть
решения: у файлов и БД одна точка фиксации.

## Последствия

- Состояние «файл опубликован, БД не знает» недостижимо при штатной работе.
- Повторный запуск стадии безопасен: предыдущая версия артефакта не теряется молча.
- Цена — `Writer` заметно сложнее обычной записи файла: временные пути, бэкапы, порядок
  отката. Это осознанная сложность, упрощать её нельзя.
- Порядок вызовов обязателен: `Stage*` → `Commit(persist)`. Вариант `Commit(nil, pending)`
  публикует файл без записи в БД и должен использоваться только там, где состояние
  сохраняется другим `Commit`.

## Альтернативы

- **Транзакционная файловая система / WAL поверх файлов** — несоразмерно задаче.
- **Хранить артефакты в БД** (`BYTEA`/`TEXT`) — снимает проблему целиком, но артефакты
  нужны человеку на диске для чтения и разбора, а промпты и ответы объёмны.
- **Сначала БД, потом файл** — переносит проблему, а не решает: битая ссылка вместо сироты.

## Известное нарушение

Batch-ветка `make task-1 result` не следует этому решению: публикует файл через
`Build` (`Commit(nil, …)`), затем отдельно вызывает `CompleteGeneration`. См. H8 в
[бэклоге аудита](../AUDIT-2026-08.md).
