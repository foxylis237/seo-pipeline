# Работа с Claude Code в этом проекте

Как ставить задачи и когда вызывать скиллы. Проверено на практике этого репозитория.

## Где что доступно

| Слой | Где лежит | Действует |
|---|---|---|
| Правила проекта | `CLAUDE.md`, `.claude/rules/*.md` | подключаются сами, `rules` — по путям файлов |
| Скиллы проекта | `.claude/skills/<имя>/SKILL.md` | **только в этом репозитории** |
| Хуки | `.claude/hooks/` | сами, на каждое действие |

Скиллы доступны одинаково и в терминале, и в расширении VS Code — оба читают `.claude/`
из корня проекта. В других репозиториях их нет.

Универсальный слой `~/.claude/` сюда намеренно не подключён — см.
[ADR-0007](adr/0007-claude-code-layers.md).

## Скиллы проекта

Восемь из девяти помечены `disable-model-invocation: true` — их **запускаете только вы**,
набрав `/имя`. Сам Claude их не вызовет, даже если задача подходит.

### В начале задачи

| Скилл | Когда |
|---|---|
| `/grill [задача]` | нетривиальная задача: требования размыты, у решения несколько трактовок, меняется контракт, схема БД, внешнее поведение или архитектурная граница |

`grilling` — единственный скилл без запрета на автозапуск: он может включиться сам, если
задача похожа на описанную. `/grill` — то же самое, но по вашей команде.

### По области работы

| Скилл | Когда |
|---|---|
| `/stage-add [имя стадии]` | добавляете стадию в пайплайн генерации |
| `/prompt-tune [стадия]` | правите промпт стадии |
| `/selector-fix [интеграция и симптом]` | сломался селектор Playwright: Keys.so, Arsenkin, DeepSeek Web |
| `/db-check [таблица или колонка]` | разъехались миграции, `expectedSchema` и фактическая БД |
| `/arch-review [пакет или тема]` | нужен глубокий архитектурный разбор в отдельном контексте |

### Перед сдачей

| Скилл | Когда |
|---|---|
| `/ship [--commit]` | перед коммитом: формат, vet, линтер, тесты, race и проверка, что тесты репозитория **действительно выполнились** |
| `/prod-ready [область]` | готовность к длительной эксплуатации: таймауты, отмена, graceful shutdown |

`/ship` закрывает ловушку `TEST_DATABASE_URL`: без него 15 тестов репозитория молча
пропускаются, а `make test` при этом зелёный.

### Правила

- Вызывать **в начале** задачи. Скилл задаёт порядок действий; на полпути толку мало.
- Один скилл на задачу. Цепочка `/grill` → работа → `/ship` нормальна, три подряд — нет.
- Не брать на мелочь: однострочная правка или вопрос по коду обходятся без скилла.

Из встроенных здесь полезны `/code-review` для текущего диффа и `/simplify` — он вычищает
дублирование и лишнее в изменённом коде, но багов не ищет.

## Как формулировать задачу

Рабочая форма — цель, границы, порядок:

```
Нужно <что и зачем>.

Не менять: <pipeline / БД / миграции / промпты / архитектуру>.

Сначала: 1) изучи 2) предложи минимальное место 3) реализуй после согласования.
```

Три вещи, которые дают наибольший эффект.

**Явные запреты.** «Не добавлять колонку в `articles`», «состояние провайдера не в
PostgreSQL» отсекают половину неверных решений до обсуждения.

**Разделение на этапы.** «Сначала предложи, реализуй после согласования» позволяет
развернуть решение до того, как написан код. На архитектурных правках это дешевле любых
переделок.

**Настоящий вывод вместо пересказа.** Вставляйте лог целиком, со `stage=`, `duration_ms`
и кодами. Из него видно то, чего нет в описании: например, что стадия упала сначала на
`503`, а квота пришла только второй попыткой.

### Готовые формы

```
Разберись, почему <симптом>. Не меняй код. Покажи конкретный участок и объясни.
```
```
Найди минимальное место для <изменение>. Предложи 2–3 варианта, выбери и обоснуй.
```
```
Реализуй <что>. Тесты обязательно. Прогон не запускай.
```
```
Прогони <команда> и почини, что упадёт. Запускать разрешаю.
```

Последняя форма важна: команды `prepare`, `generate`, `run`, `retry`, `regenerate` тратят
деньги и ходят во внешние сервисы с риском бана, поэтому без явного разрешения не
запускаются. Если запуск нужен — скажите прямо. Если не нужен — скажите тоже, фраза
«сделай всё» этого не выражает.

### Что мешает

- **Несколько задач в одном сообщении.** Приоритеты приходится угадывать.
- **Размытые команды** вроде «сделай всё», «оптимизируй», «улучши» — нет критерия успеха.
- **Смешение «не меняй код» и «исправь»** в одном сообщении. Выберите одно.

## Терминал и VS Code

| | VS Code | Терминал |
|---|---|---|
| Сильная сторона | правки видно диффом, выделенный код и открытый файл уходят в контекст сами | долгие фоновые прогоны, несколько сессий, `--resume` |
| Брать для | разбора и правки кода, ревью диффа | `make task-1 …`, отладки Playwright, всего, что идёт 10+ минут |

Сессии раздельные: контекст между окном VS Code и терминалом не общий.

Полезное в терминале: `claude --continue` возвращает последнюю сессию, `claude --resume`
даёт выбрать из списка, `claude -p "..."` — разовый вопрос без сессии, в том числе с
пайпом (`git diff | claude -p "что здесь рискованно"`). `Esc` прерывает текущее действие,
не убивая сессию. Shift+Tab переключает режим, включая plan mode — в нём правки запрещены
механически, а не на доверии, и это правильный режим для «сначала разберись».

`/clear` — при смене темы. Длинная сессия сжимается автоматически, детали теряются.

Точный список команд и флагов зависит от версии: `claude --help` и `/help`.

## Чего не делать

**Не запускать `make task-1` параллельно в двух окнах.** Профиль браузера DeepSeek один и
защищён `flock`; второй процесс упадёт на стадии `structure` с невнятной ошибкой 503.

**Не давать общее разрешение на команды, которые тратят деньги.** Разрешать пачкой
безопасно только чтение: `git`, `go test`, `grep`, `docker ps`.

**Не рассчитывать на память между сессиями.** То, что должно пережить перезапуск, просите
записать явно — в ADR, в задачу или в память проекта.
