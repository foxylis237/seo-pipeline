# Критичные

## C1. Dry-run сломан: stub-модель не доходит до роутера {#c1}

`dry_run.go:128` подменяет `stage.Model` на `dry-run-<stage>`, но `Router.generateTarget`
формирует запрос из `target.Model` (`llm.go:250`). `validateLLMConfig` всегда заполняет
`stage.Targets`, поэтому ветка `if len(stage.Targets) == 0` не срабатывает. В stub приходит
реальное имя модели.

Проверено экспериментально:

```
router.Generate(structure) err = LLM stage "structure" failed for all attempted targets:
  provider=gemini model=gemini-2.5-flash: dry-run has no response for model gemini-2.5-flash
```

Затронуты `structure`, `review`, `fix`, `html`. Стадии `article`/`info` идут через
`chatFactory` и работают.

**Критичность.** Единственный способ проверить пайплайн без денег и внешних сервисов
не работает, и это гейт в `make task-1 dry-run`.

**Как чинить.** Переписывать `stage.Targets`, а не `stage.Model`:

```go
for name, stage := range llmConfig.Stages {
    stage.Model = dryRunModelPrefix + name
    for i := range stage.Targets {
        stage.Targets[i].Model = dryRunModelPrefix + name
    }
    llmConfig.Stages[name] = stage
}
```

Плюс устранить первопричину (H5) и добавить тест, прогоняющий `runDryRun` через настоящий
`LoadLLMConfigForDryRun`, а не только `dryRunClient` изолированно.

**Файлы.** `cmd/seo-pipeline/dry_run.go`, `cmd/seo-pipeline/dry_run_test.go`, `internal/llm/llm.go`

## C2. Dry-run не стартует на свежем клоне {#c2}

`.env.example` содержит пустой `GEMINI_MODEL=`. `config.yaml` объявляет target
`{provider: gemini, model: "${GEMINI_MODEL}"}`. Флаг `requireCredentials=false` отключает
только проверку API-ключа, но не проверку модели (`config/llm.go:126-128`).

Проверено: `FRESH CLONE (no model env): err = LLM stage "structure" target 0 has empty model`.

README при этом обещает безопасную проверку сразу после `cp .env.example ../.env`.

**Критичность.** Первое, что советует README, не работает.

**Как чинить.** В dry-run не валидировать `model` вообще — он всё равно подменяется.
Вариант «непустые дефолты в `.env.example`» хуже: маскирует, а не чинит.

**Файлы.** `internal/config/llm.go`, `.env.example`, `README.md`

## C3. Все 15 тестов репозитория молча пропускаются {#c3}

`article_repository_test.go:919-924` требует `TEST_DATABASE_URL`, иначе `t.Skip`. Переменная
не упоминается **ни в Makefile, ни в README, ни в `.env.example`, ни в docker-compose**.

```
internal/tasks/task1/repository   ok   coverage: 0.0% of statements
```

1046 строк тестов не выполняются никогда. Покрытие слоя данных — ноль, при этом `make test`
рапортует `ok`. Хуже: `make task-1 dry-run` использует `go test ./...` как гейт — гейт
зелёный, хотя из БД не проверено ничего. Инвариант `SKIP LOCKED` фактически не тестируется.

**Измерено 2026-08-05** — тесты запущены с заданной переменной, впервые:

```
TEST_DATABASE_URL='postgres://seo:seo@localhost:5433/seo_dry_run?sslmode=disable' \
  go test -count=1 -cover ./internal/tasks/task1/repository/...
ok  ...  coverage: 63.5% of statements
```

15 тестов, 0 пропущено, 0 упало. То есть тесты **рабочие и зелёные** — проблема ровно в том,
что их никто не запускает: покрытие слоя данных меняется с 0.0% на 63.5% от одной переменной
окружения. Это делает находку дешёвой в закрытии и повышает её приоритет.

**Как чинить.**
1. Цель `test-db` в Makefile: поднять `postgres-dry-run` и экспортировать
   `TEST_DATABASE_URL='postgres://seo:seo@localhost:5433/seo_dry_run?sslmode=disable'`.
2. Задокументировать переменную в README и `.env.example`.
3. Сделать пропуск громким: сводка пропущенных тестов в конце `make test`, в CI — `t.Fatal`.

Частично закрыто скиллом `/ship`: он проверяет, что тесты репозитория реально выполнились.

**Файлы.** `Makefile`, `README.md`, `.env.example`, `internal/tasks/task1/repository/article_repository_test.go`

## H2. Keys.so — единственная интеграция без блокировки профиля {#h2}

Arsenkin (`arsenkin/client.go:131-139`) и DeepSeek (`deepseekweb/browser.go:26-34`) берут
`syscall.Flock(LOCK_EX|LOCK_NB)` на lock-файл в каталоге профиля. Keys.so
(`keysso/client.go:216-231`) — нет: `MkdirAll` и сразу `LaunchPersistentContext` на
захардкоженный `data/keysso-browser-profile`.

Два параллельных `make task-1 prepare` — штатный сценарий (см. [ADR-0002](adr/0002-skip-locked.md)) —
откроют один профиль Chromium. Итог: повреждение LevelDB, потеря сессии, ручной релогин.
`prepare` — самая долгая операция, желание запустить два процесса естественно.

Дополнительно: `profilePath` — константа пакета, изоляция невозможна даже вручную.

**Критичность.** Тихая порча состояния, воспроизводится под нагрузкой, диагностируется тяжело.

**Как чинить.** Скопировать паттерн Arsenkin: lock-файл + `Flock` + `releaseProfile()` в
`Close()`. Заодно вынести общий `launchBrowser` в `internal/browser/profile.go` — сейчас
он продублирован трижды почти дословно.

**Файлы.** `internal/integrations/keysso/client.go`, `internal/integrations/arsenkin/client.go`,
`internal/llm/deepseekweb/browser.go`

## H5. Два источника истины для маршрутизации LLM {#h5}

`LLMStageConfig` хранит и легаси-поля `Provider`/`Model`, и `Targets []LLMTargetConfig`.
Синхронизация — одна строка: `stage.Provider, stage.Model = stage.Targets[0].Provider,
stage.Targets[0].Model` (`config/llm.go:131`). Дальше:

- `Router.Prepare` возвращает `stage.Provider`/`stage.Model` (легаси, `llm.go:323`);
- `Router.generateTarget` использует `target.Provider`/`target.Model` (`llm.go:250`);
- `dry_run.go` пишет в легаси → **C1**.

C1 — не опечатка, а прямое следствие дублирующегося состояния. `PreparedCall.Provider`/`Model`
нигде не читаются, кроме `articleCall.Model` в логе (`pipeline.go:278`) — и там логируется
первый target, даже если сработал fallback. **Лог врёт.**

**Как чинить.** Удалить `Provider`/`Model` из `LLMStageConfig`, оставить только `Targets`.
YAML-совместимость (одиночный `provider`/`model`) обрабатывать во временных полях парсинга
и схлопывать в `Targets` при валидации. Из `PreparedCall` убрать `Provider`/`Model`, оставить
`Prompt`+`Timeout`; в лог писать фактический `result.Model` после ответа.

**Файлы.** `internal/config/llm.go`, `internal/llm/llm.go`, `cmd/seo-pipeline/dry_run.go`,
`generation/pipeline.go`

## H6. Нет общего бюджета времени: таймауты умножаются {#h6}

Таймауты вложены и не согласованы:

1. `Pipeline.runArticleAndInfo` оборачивает `ctx` в `WithTimeout(articleCall.Timeout)` (`pipeline.go:279`);
2. `Router.generateTarget` ещё раз `WithTimeout(stage.Timeout)` (`llm.go:251`) — **на каждый
   target отдельно**, от родительского ctx;
3. внутри — до 3 попыток с паузами;
4. `gemini.chatSession.Generate` добавляет свой хардкод `requestTimeout = 5 * time.Minute`
   (`gemini/client.go:16`), не связанный с конфигом.

Для стадии `fix` (`timeout: 300s`, 2 target'а) худший случай — 10 минут на одну стадию.
По шести стадиям — до ~30 минут на статью, без `prepare` (Wordstat 300 с + Copywriters 600 с).
Batch по 50 статьям непредсказуем; верхнего предела не задано.

**Критичность.** Процесс может «висеть» часами без индикации, что что-то не так.

**Как чинить.** `WithTimeout` на статью в `runSelectedArticles`; `stage.Timeout` трактовать
как бюджет **на всю стадию включая fallback** (создавать `stageCtx` в `generatePrompt`,
а не в `generateTarget`); убрать хардкод в gemini, брать дедлайн из ctx; добавить в конфиг
`article_timeout` и `batch_timeout`.

## H7. `SaveStructurePath` молча обнуляет нижележащие пути {#h7}

`article_repository.go:763-774`:

```sql
ON CONFLICT (article_id) DO UPDATE
SET structure_path = EXCLUDED.structure_path,
    article_path = NULL, metadata_path = NULL,
    html_path = NULL, final_path = NULL, word_count = NULL,
```

Файлы `article.txt`, `review.txt`, `fixed_article.txt`, `article.html` **остаются на диске** —
БД просто перестаёт на них ссылаться. Поскольку `Pipeline.Run` всегда начинается со `structure`,
повторный `make task-1 generate 37` для готовой статьи осиротит все её артефакты.
Комментарий метода об этом не говорит; README обещает обратное для `retry`/`demo-generate`.

**Как чинить.** Либо не обнулять (пусть `GetPendingForOperation` разбирается по `current_step`),
либо обнулять явно и логировать `WARN` со списком осиротевших путей, либо переносить старые
артефакты в `generated/.superseded-<ts>/`. Как минимум — задокументировать.

## H8. Неатомарная финализация в batch-режиме `result` {#h8}

Два пути завершения статьи ведут себя по-разному:

- **demo/quick** (`pipeline.go:194-203`): `BuildStaged` → `Commit(func(){ CompleteGeneration })` —
  файл и статус фиксируются атомарно, с откатом файла при сбое БД. Правильно.
- **`make task-1 result`** (`main.go:112-121`): `resultService.Build()` (внутри `Commit(nil, ...)` —
  публикует файл) → отдельный `GetResultInput` → отдельный `CompleteGeneration`. Три
  независимые операции.

Падение между ними даёт `result.md` на диске при `status='processing'`. `Build` внутри
полного `Pipeline.Run` (`pipeline.go:141-148`) страдает тем же.

**Критичность.** Непоследовательность в единственном месте, где проект специально построил
механизм атомарности ([ADR-0001](adr/0001-staged-commit.md)).

**Как чинить.** Везде `BuildStaged` + `Commit(persist)`. Метод `Build` — удалить или сделать
приватным. Заодно уйдёт лишний `GetResultInput`.

## M14. Утечка goroutine heartbeat при панике клиента {#m14}

`llm.go:269-271`:

`stopHeartbeat` не защищён `defer`. Паника внутри `client.Generate` (реальный риск: Playwright-

## M19. Колонки путей хранят не то, что означают их имена {#m19}

**Добавлена 2026-08-05**, при подготовке скилла `/stage-add`. В исходном аудите не было.

Фактическое содержимое колонок `article_outputs`:

| Колонка | Что в ней лежит |
|---|---|
| `structure_path` | `generated/structure.txt` — соответствует |
| `article_path` | `generated/article.txt` — соответствует |
| `metadata_path` | **`generated/review.txt`** — не метаданные |
| `final_path` | **`generated/fixed_article.txt`** — не итоговый файл |
| `html_path` | `article.html` — соответствует |

`SaveReviewPath` пишет путь ревью в `metadata_path` (`article_repository.go:841`),
`SaveFixedArticlePath` пишет исправленную статью в `final_path` (`:865`). Метаданные при
этом хранятся не здесь вовсе — `SaveArticleInfo` пишет их в таблицу `article_metadata`.

Путь `result.md` **не сохраняется нигде**: `CompleteGeneration` ставит только
`status='completed'` и `current_step = NULL`. Восстанавливается из `external_id` + `slug`.

Усугубляет то, что NULL-ность этих колонок работает как **машина состояний** в
`GetPendingForOperation` (`:669-682`):

```
review ждёт → metadata_path IS NULL
fix    ждёт → metadata_path IS NOT NULL AND final_path IS NULL
html   ждёт → final_path   IS NOT NULL AND html_path   IS NULL
```

То есть колонка — не хранилище пути, а часть логики выборки. Читающий код `GetPendingForOperation`
не может понять предикат, не зная о подмене смысла.

**Критичность.** Средняя. Данные не теряются, но любая работа с этими колонками начинается
с неверной гипотезы: добавление стадии, отладка «почему статья не берётся в выборку»,
попытка вывести путь ревью пользователю.

Связана с M4 (мёртвые колонки) и H7 (`SaveStructurePath` обнуляет эти же колонки) —
все три про то, что `article_outputs` спроектирована не под текущий набор стадий.

**Как чинить.** Переименовать колонки миграцией под фактическое содержимое
(`review_path`, `fixed_article_path`) с синхронной правкой `expectedSchema` и трёх
предикатов выборки. Либо — если решено оставить — задокументировать подмену прямо
в комментарии к `expectedSchema`, чтобы она перестала быть скрытой.

**Файлы.** `internal/tasks/task1/repository/article_repository.go`,
`internal/tasks/task1/repository/schema.go`, новая миграция

невнятные ошибки, автодополнение целей не работает. Альтернатива — переменные
(`make task-1 OP=generate ID=37`) или отдельные цели.

## Конкретные пробелы

1. **Wiring-тест dry-run** — самый важный. Ни один тест не прогоняет `runDryRun` через
   настоящий `LoadLLMConfigForDryRun` + `NewRouter`; существующие проверяют `dryRunClient`
   изолированно, поэтому C1 не был пойман.
2. **`output.Commit` — сценарии отката.** 71% при том, что откат из hard-link-бэкапа — самая
   тонкая логика в проекте. Нет тестов: сбой `persist()` при существующем целевом файле;
   сбой `rename` на втором из трёх файлов; двойной `Commit`; `Abort` после `Commit`.
3. **Keys.so/Arsenkin классификаторы.** `resultError`/`isRetryableResultError`/`waitKeywordsResults`
   покрыты на 13.9% — а именно они определяют, будет ли статья бесконечно ретраиться.
4. **End-to-end пайплайна.** Нет теста «импорт → research (стаб) → все 6 стадий → result.md»
   на in-memory фейках. `pipeline_test.go` тестирует стадии по отдельности.
5. **`storage`** — нет теста, что `NewPostgres` закрывает пул при неуспешном `Ping`.
6. **`ValidateSchema`** — нет теста на реальной БД с намеренно испорченной схемой.
7. **Race-тесты** для `deepseekweb.Client` (параллельные `Generate` + `Close`) и heartbeat в `llm`.
