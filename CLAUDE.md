# SEO Pipeline

Go CLI: импорт статей из Excel → сбор SEO-данных (Keys.so, Arsenkin через Playwright) →
генерация текста через LLM → сборка `result.md`. Состояние в PostgreSQL, артефакты на диске.
Реализован один сценарий — `task_1`.

## Команды

| Команда | Назначение |
|---|---|
| `make help` | Список всех целей |
| `make test` | `go test ./...` |
| `make test-race` | Race detector (сейчас только `task1` — см. Ловушки) |
| `make lint` | golangci-lint |
| `make vet` / `make fmt` | Статический анализ / форматирование |
| `make build` | Бинарник в `bin/seo-pipeline` |
| `make docker-up` / `docker-stop` | PostgreSQL (5432 рабочая, 5433 dry-run) |
| `make task-1 import [limit]` | Импорт из `input/task_1/input.xlsx` |
| `make task-1 errors [external_id]` | Статьи с сохранёнными ошибками |

`make task-1 <operation> [id]` — единая точка входа. Без ID обрабатываются все подходящие
статьи, с ID — одна. `<id>` это `external_id` из Excel, не `articles.id`.

## Архитектурные принципы

Clean Architecture — **как границы, а не как структура папок**. Слои не плодим; следим за
направлением зависимостей и за тем, чтобы бизнес-сценарии не знали про CLI, PostgreSQL,
Playwright и конкретных LLM-провайдеров.

DDD — **только тактически**: единый язык (`docs/CONTEXT.md`) и явные модели статьи, этапа,
статуса, ошибки, результата. Агрегаты, bounded contexts и domain events не вводим, пока нет
реальной бизнес-потребности.

Главный критерий при проектировании — **OCP**: новый этап пайплайна, SEO-интеграция,
LLM-провайдер или точка входа должны добавляться **без правки существующей бизнес-логики**.
Если добавление требует трогать работающий код — это сигнал, что граница проведена не там.

EDA и Vertical Slice сейчас не внедряем, но решения не должны закрывать к ним путь.

Изменения — постепенные и только там, где они снижают связанность, повышают понятность или
упрощают расширение. Рефакторинг ради соответствия шаблону не делаем.

## Инварианты

Ломать их без явного обсуждения нельзя:

- **Атомарность «файлы + БД»**: артефакты пишутся во временные файлы, публикуются `rename`,
  состояние в БД сохраняется через `articleoutput.Commit(persist, pending...)`. При сбое
  `persist` файлы откатываются на предыдущую версию. Не публиковать файл отдельно от статуса.
- **`FOR UPDATE SKIP LOCKED`** в `ClaimNextIncomplete` — конкурентные процессы не получают
  одну статью. Не заменять на `SELECT ... LIMIT 1`.
- **`repository.ValidateSchema`** сверяет колонки, типы, nullable и каскадные FK перед каждой
  командой. Новая миграция ⇒ обязательная правка `expectedSchema` в `schema.go`.
- **Пути в БД относительны `OUTPUT_DIR`**, не абсолютны.
- **Persistent-профили браузера защищены `flock`** (Arsenkin, DeepSeek). Два процесса на один
  профиль портят его.

## Ловушки

Проверено, легко наступить повторно:

- **`TEST_DATABASE_URL` нигде не задан**, поэтому все 15 тестов `internal/tasks/task1/repository`
  молча пропускаются, а покрытие слоя данных — 0%. `make test` при этом зелёный.
- **`make task-1 dry-run` не работает**: `dry_run.go` подменяет `stage.Model`, а роутер читает
  `stage.Targets[i].Model`. На чистом клоне падает раньше — из-за пустого `GEMINI_MODEL`.
- **`.env` ожидается на уровень выше корня проекта** (`../.env`), переопределяется `ENV_FILE`.
- **`go.mod` требует Go 1.25.0**, локально 1.24.4 — тулчейн подгружается автоматически.
- **`make test-race` покрывает только `./internal/tasks/task1/...`**, а конкурентность живёт
  в `internal/llm` (heartbeat-goroutine) и `internal/llm/deepseekweb` (mutex + семафор).
- **`article` и `info`** — два имени одной объединённой операции.

Полный разбор: `docs/AUDIT-2026-08.md`.

## Конвенции

- Ошибки оборачиваются с контекстом: `fmt.Errorf("что делали: %w", err)`.
- Классификация ошибок — через `errors.As` по типам (`llm.StatusError`, `keysso.StageError`,
  `arsenkin.StageError`, `generation.StageError`), **не** по подстрокам сообщения.
- Именование в коде и тестах — из `docs/CONTEXT.md`.
- Коммиты — Conventional Commits, как в истории: `feat:`, `fix(task1):`, `refactor(task1):`,
  `chore:`, `docs:`. Без co-author трейлеров.
- Комментарии и сообщения об ошибках сейчас смешаны RU/EN. Новый код — английский;
  пользовательский вывод CLI — русский.

## Границы

- `make task-1 prepare|generate|run|retry` **тратят деньги** (LLM) и ходят во внешние сервисы
  (Keys.so, Arsenkin) с риском бана аккаунта. Не запускать без явной просьбы.
- `data/` содержит живые Cookies Keys.so и Arsenkin. Не читать, не логировать, не коммитить.
- Незакоммиченная работа в дереве может быть чужой фичей в процессе — не сметать её
  в общий коммит.

## Где что искать

- Правила по слоям — `.claude/rules/` (подключаются автоматически по путям файлов).
- Автоматические проверки — `.claude/hooks/` (gofmt+vet на Go-файл, напоминание про
  `expectedSchema` на миграцию, контекст при старте, защита `data/` и `tasks/*/output/`).
- Процедуры — `/` (skills). Начать с `/grill` для нетривиальной задачи и `/ship` перед коммитом.
  Архитектурный разбор области — `/arch-review`. Проектные процедуры: `/stage-add`,
  `/db-check`, `/selector-fix`, `/prompt-tune`, `/prod-ready`.
- Диагностика прогона — в каталоге самой статьи: `<external_id>-<slug>/prepare/`
  (`input.json`, `keysso.json`, `arsenkin.json`, `prepare-report.json`) и
  `<external_id>-<slug>/logs/<операция>.log`. Пишет приложение, `tee` не нужен.
- Единый язык — `docs/CONTEXT.md`.
- Архитектурные решения — `docs/adr/`. Конфигурация Claude Code целиком живёт в `.claude/`;
  универсальный слой в `~/.claude/` сюда намеренно не подключён — см. ADR-0007.
